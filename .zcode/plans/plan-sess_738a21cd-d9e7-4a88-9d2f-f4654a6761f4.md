# 修复：第二条入库被写上第一条的淘宝商品ID

## 根因（两处叠加缺陷）

**缺陷A（触发器）— 导航守卫顺序错误**：第一条发布成功后，淘宝把发布页 URL 改写成 `publish.htm?itemId=第一条ID&fromAiPublish=true`（这是提交成功的正常形态，`submit.js` 甚至以 URL 含 itemId 为成功判据），该标签被 `run_batch` 尾部 `_prune_tabs(keep_url=session.href())` 保留为活动标签。第二条开始时 `need_new_tab=True` 本应直接新开类目页，但 `ensure_fill_tab`（pipeline.py:302）在 `force_new` 分支**之前**就对这条旧页面 URL 执行 `assert_safe_url`，URL 含 `itemid=` 直接抛 `UnsafeUrl("拒绝使用已有商品编辑页…")`，第二条还没开始就失败。`ensure_new_category_tab`（pipeline.py:333）内部还有一处同样守卫会拦截；CLI 侧 `open_new_publish`（千牛网页执行.py:1399）同病。

**缺陷B（放大器）— 失败文案刮取商品ID不校验归属、不区分成败**：失败 notice（含被拒 URL）和结果 `url`（= 残留编辑页）进入记录后，`job_session.product_action_links`（job_session.py:76-79）用正则从任意文本刮 `itemId=(\d{8,})`，经 `patch_execution`（job_session.py:426→442-458）写入 job_session.json，经 `desktop/jobs.py serialize_row→_action_links→on_done`（jobs.py:1260/1274）写入内存 rows → 执行明细里第二条显示第一条的 ID，并进入结果 xlsx/json。项目已有"失败态不给 ID"的约定（`material_import.item_id_from_result`，material_import.py:188-189），但这条路径没有对齐。

**连锁**：`_pending_products`（jobs.py:988-1028）重跑时把错 ID 当 prior_id 合并进商品数据 → 第二条走"已有商品"分支 → 打开第一条的编辑页 → 触发"标题不符，禁止再次建品"暂停。

## 修改内容

### 1. `web_fill/pipeline.py` — `ensure_fill_tab`（治本）
把 `force_new` 分支提到守卫之前；删除对"旧活动页"的 `web.assert_safe_url(href)`（第 302 行）。当前页不可复用时自然走"找其他干净发布页 → 找类目页 → 新开类目页"，全程不会在编辑页上执行填表（防线仍在：`_is_reusable_publish` 排除编辑页、pipeline.py:1914-1916 对新发布页断言、JS 侧 `unsafeUrl` 兜底）。

### 2. `web_fill/pipeline.py` — `ensure_new_category_tab`
删除第 332-333 行对旧活动页的 `assert_safe_url`（该函数只 `tab_new` 新标签，不碰当前页；保留第 359 行对新开类目页的检查）。

### 3. `job_session.py` — 失败态刮取守卫（防复发）
新增常量 `FAIL_EXECUTIONS = frozenset({"失败", "暂停", "提交失败", "已停止"})`；`product_action_links`/`apply_action_links` 增加 `execution` 参数（`apply_action_links` 缺省从 `target.get("execution")` 取），命中失败态时跳过 `_ITEM_ID_RE`/`_CAT_ID_RE` 的文本刮取；显式可信来源（`submitted.itemId`、`item["taobao_item_id"]`，即"提交成功但验收失败"续跑场景的真实 prior_id）不受影响。"结果待核实/提交待核实"态保留刮取（notice 里"商品ID: xxx"供人工核实）。`patch_execution` 调用处显式传 `execution`。这样 `desktop/jobs.py` 的 `_action_links`/快照渲染自动获得守卫。

### 4. `千牛网页执行.py` — `open_new_publish`（CLI 同病同修）
删除第 1399 行 `goto` 前对旧页的 `assert_safe_url(session.href())`；保留第 1403 行（类目页）与第 1430 行（新发布页逐秒检查）的守卫。

### 5. `web_fill/pipeline.py` — `run_batch` 存量污染防御
在循环读取 `prior_id`（约 2320 行）处：若该商品状态 ∈ 失败类 且 notice 含"拒绝使用已有商品编辑页" 且 `prior_id` 出现在 notice 中（本 bug 的精确指纹，说明 ID 来自被拒 URL 的刮取），丢弃 `prior_id` 按全新建品处理。不误伤"提交成功但验收失败"的真 ID（其 notice 不含该文案）。已被污染的第二条记录重跑后会被真实新 ID 覆盖；也可在执行明细中手动"清除记录"。

### 6. `test_web_fill.py` — 新增单元测试（非浏览器）
- 失败/暂停/提交失败/已停止态：notice 带 `itemId=` 不产出 `taobao_item_id`/链接；显式 `item["taobao_item_id"]` 保留。
- `ensure_fill_tab(force_new=True)`：活动标签是 `publish.htm?itemId=…` 编辑页时不抛 `UnsafeUrl`，正常走新类目页。
- `run_batch`：污染记录（失败 + 拒绝文案 + ID 在 notice 里）丢弃 prior_id 走 `fill_new_product` 新建分支。

最后运行 `python -m unittest test_web_fill test_web test_desktop` 等相关非浏览器测试回归。

## 不改的部分（说明）
- 成功后浏览器停留在该商品编辑页、失败时保留现场的设计不变（断点续跑依赖它）。
- 存量 job_session.json 中已写入的错 ID 不做批量清洗（无法与真实 prior_id 区分来源）；重跑自动纠正 + 手动"清除记录"两条路径已覆盖。
